## 问题与原因

线上任务在已保存三批文件后，因 `请先读取最新文件 README.md。` 停止。该提示来自平台的写入前置检查，不是模型 API 超时，也不是缺少 README 文件。已有文件必须先读取；读取记录绑定整个工作区的 `head`，因此保存其他文件后，旧读取记录也会过期。

此前 `apply_changes` 对此抛出异常，SDK 将工具异常视为任务失败。Agent 虽然收到了“出现冲突时重新读取”的指令，却没有继续调用工具的机会。

## 修复后的行为

- 未读取现有目标文件或提供旧 `head` 时，本批不写入任何文件。工具向 Agent 返回结构化反馈：`ok:false`、`recoverable:true`、`code`、当前 `head`、`requiredReads` 和下一步说明。
- Agent 应逐一读取指定文件，结合最新正文重新生成变更并使用最新版本保存；不是原样重复发送旧正文。没有现有目标文件时重新列出工作区获取版本。
- 进度显示“需要重新读取”和“本次未保存”，随后记录实际读取和保存。不会把这次被阻止的写入展示成已保存。
- 每轮最多返回三次此类恢复反馈，第四次停止；仍受原有最多24回合、10分钟限制。若 Agent 忽略反馈直接结束，平台报告未完成，不把未保存的变更当成成功。
- 已成功保存的文件保留。恢复步骤是同一 Agent 任务中的后续工具操作，可能增加模型用量；不会自动重试失败的模型 HTTP 请求。

## 保留的边界

本次只恢复写入前可明确识别的缺少读取或旧版本。路径/权限错误、未读取技能、任务停止、执行租约失效、Runner断线和写入期间发生的并发冲突等继续明确停止。不能把所有HTTP 409/502都当成文件版本冲突，更不能在结果不明确时自动重复写入。

底层版本校验继续执行，不能覆盖未读取的新内容。现有多文件本地写入也不因此变成文件系统事务。命令审批、Docker限制、技能版本冻结、模型配置和任务预算均遵循既有规则。

服务端即可处理本次结构化恢复，Runner协议没有变更，不需要因本次补修重新配对。
