**文档对应源码版本：2026-11-11。** 本版包含文档清单确认、方案/执行双页签、工作区 Agent 和本地 Runner；本次源码更新未部署服务器，最近的在线部署记录仍为 2026-11-09。最新浏览器组合 42/42、另五项集成用例分次通过，方案离线回归 15/15，类型检查、ESLint 和生产构建通过；独立 MySQL、网页与 Runner 联合验收使用本机模型夹具，独立 Node 测试 5/5。新入口的真实模型 + Docker 全链路仍待授权验收，2026-11-10 的真实模型成功记录使用预置技能，不能替代新入口验证。范围见[本版说明](RELEASE_NOTES_20261111.md)及[验收报告](PLAN_WORKFLOW_VALIDATION_20261111.md)。在线站点缺少执行页签时，应先由维护者部署此版。

本手册覆盖账号与项目、研究 Markdown 生成、把 Markdown 作为技能交给工作区 Agent、本地目录执行、GitHub 仓库执行、RAG 配置、常见故障和当前未完成事项。开发环境安装细节另见根目录 [README](../README.md)，本地 Runner 的完整限制见[Runner 说明](LOCAL_RUNNER.md)。

## 先理解工作流程

内容准备与实际执行分为以下路径：

| 目标 | 使用位置 | 结果保存在哪里 | 状态 |
| --- | --- | --- | --- |
| 把需求整理成方案 | 「生成方案」→「预览文档清单」→ 编辑 1–20 份 →「确认并生成 N 份文档」 | 确认生成后保存到数据库的 Markdown；默认推荐 `PLAN.md` 和 `TASKS.md` | 预览不调用模型、不联网；正文生成需要模型，不修改项目、不运行测试 |
| 先聊天，或明确要求联网调研后生成 Markdown | 「本次操作」显式选择「仅讨论」，再发送 | 数据库中的对话、研究证据和文件 | 普通聊天不强制研究；联网调研须配置真实搜索 Provider |
| 让 Agent 按 Markdown 技能修改本地目录 | 「执行工作区」页签选择「本地工作区」 | 你选择的电脑目录 | 本机验收通过；新基线尚未部署，Runner 需手动安装和配对 |
| 让 Agent 修改项目的 GitHub 仓库 | 同一区域选择「GitHub 仓库」 | 服务器上的任务分支，待人工审查 | 有实现与局部测试；完整 Agent 工作流尚未联合验收 |

项目内有两个页签：「方案与文档」集中显示研究对话和 Markdown；「执行工作区」集中显示工作方式、技能、执行要求、任务进度与差异。首次进入默认显示方案页签。生成文档后点击「使用这些文档继续执行」，会自动切到执行页签，预选当前研究包的技能并带入原目标；你可以编辑要求、增减技能和选择工作方式，再手动点击「开始执行」。交接本身不会启动任务，不会跳过命令审批。也可以直接进入执行页签输入要求创建任务，不会先替你生成方案文档。

顶部导航固定显示项目名与当前连接状态。本地方式显示选中 Runner 的实际目录和在线状态，目录可展开或复制；GitHub 方式显示仓库是否已关联。有本机命令等待批准时，执行页签显示待审批数量，点击「查看待审批命令」进入执行页签逐条处理。切换页签会保留对话草稿、文档清单修改、Markdown 编辑、所选技能、Runner、执行要求及已打开的任务差异，不会自动发起模型任务。

执行页签优先显示当前任务；无进行中任务时展示最近任务。其他已结束的任务收在默认折叠的「历史任务」中，展开后可查看旧进度、差异或按原权限继续执行。项目「个人 Agent 与任务收件箱」也默认收起，点击标题展开；从「我的下一步」进入具体任务仍会自动展开并定位。

桌面上，对话与文档面板等高，内容各自滚动，输入区固定在对话面板底部；移动端竖向排列。右侧没有已保存文档时，已有对话会显示「根据当前需求规划文档」，点击后仍先确认清单。清单与已保存的文档分开展示，预览期间仍可浏览旧文件；清单尚不是文件，不能作为技能交接。

研究进度只展示研究与文档事件；每张执行任务卡只展示该任务的执行进度。生成方案完成表示文件已保存，不代表联网核实、项目修改或测试已经完成。

Markdown 技能由平台从当前项目的研究文件中选择，并在任务创建时固定正文、来源和版本。Agent 必须调用 `read_skill` 读取所选技能后才能修改文件。浏览或下载 Markdown 不影响传递；本地工作区不会额外把技能副本写到你选定的目录中。这里的技能是 ScenarioForge 内部的任务技能格式，不会自动导出为其他 Agent 客户端的标准 `SKILL.md` 包。

## 账号与项目

1. 打开部署方提供的 ScenarioForge 地址并注册或登录。新账号需要加入团队项目时，先登录，再输入项目邀请码。
2. 从「我的项目」创建项目，或打开你已有成员权限的项目。项目成员可访问项目空间中的研究包、文件和团队 Git 工作区；个人资料和个人 Agent 偏好仍按账号隔离。
3. 项目创建者可在项目设置中维护项目模型 API 配置。服务端也可以提供默认模型配置。API 密钥保存在服务端，不要把它粘贴到研究内容、Runner 命令或本地项目文件中。
4. 在开始真实研究前确认模型 API 可用，并确认搜索 Provider 不是 `mock`。Mock 搜索返回的是带明确标记的测试数据，不能作为研究证据。搜索 Provider 由平台维护者在服务端配置，不是项目中的 Embedding 设置。

当前开发基线还未部署到在线服务器。下文涉及工作区 Agent 的步骤，只有在运行了包含该基线和对应数据库迁移的实例上才可操作。

## 准备方案与研究 Markdown

### 路径一：确认文档清单后生成方案

1. 在「研究与对话」输入目标、范围、约束、交付物和验收标准。需要具体材料时上传 Markdown、UTF-8 TXT、含文本 PDF 或 DOCX；扫描 PDF 不执行 OCR，文件数和大小以页面限制为准。
2. 保持「本次操作」默认的「生成方案」，点击「预览文档清单」。首次输入和已有对话采用相同规则，无需先聊天或先跑外部搜索。已有对话有补充要求时先填写，再预览；留空时使用原目标。右栏没有文档时也可点击「根据当前需求规划文档」。此时只展示清单，不会生成文件或调用模型。
3. 在右栏「确认文档清单」检查每份文件的名称、用途和内容要点。默认推荐 `PLAN.md`（方案）和 `TASKS.md`（任务与验收）；需求中出现「数据库」「接口设计」「实验」「测试策略」等明确关键词时，会建议相关模板。推荐使用本地规则，不联网，不是 AI 语义规划，也不保证理解了所有隐含需求；请自行调整。可以从下拉框添加模板、添加自定义文档、逐项修改或移除，最终保留 1–20 份。内容要点每行一条，用途与要点不能为空。
4. 文件名须以英文字母开头，仅使用英文字母、数字、下划线和连字符，名称主体最多 80 个字符，以 `.md` 结尾；不能含目录、系统保留名或忽略大小写后的重名。例如 `API_DESIGN.md` 有效，`docs/API.md`、`notes.txt`、`NUL.md` 无效。提示错误时先修正，确认按钮才可用。
5. 点击「确认并生成 N 份文档」才会调用一次模型，按确认的清单生成正文，无自动重试。这一步不联网、不执行代码，也不能证明方案或建议命令已经验证。暂不需要时点击「暂不生成」；这只收起清单，不生成正文，刷新页面仍可恢复已保存的清单。修改需求后应重新预览并确认。
6. 生成完成后，在「研究文档」检查正文，按需要编辑并保存；保存后产生新版本，也可以只浏览。下载单个文件或 ZIP 完全可选，不影响后续作为技能传给 Agent，ZIP 也不会自动导入本机目录。

未列入本次清单的旧文件会保留，不会因减少份数而删除。若某个所选目标已被手动修改并保存，自动生成会拒绝覆盖；请从清单移除该目标、使用新的文件名或继续手动完善。生成前先保存或取消编辑、回答阻塞问题，并等待当前任务结束。预览后资料或文档变化时，会提示「资料或文档已更新，请重新预览清单」，当前输入保留，确认被禁用；先记录需要保留的修改，再点击「重新预览清单」检查新建议。生成接口返回冲突也会保留清单输入；生成期间发生变化时，系统拒绝保存过期结果。

### 路径二：先讨论或明确要求联网调研

在「本次操作」显式选择「仅讨论」，再点击「发送」，用于聊天、澄清需求或安排研究；首次输入和已有对话都需这样切换。普通聊天回复不会自动保存成方案文件，也不强制执行外部研究。需要来源时明确提出联网调研目标，并确认服务端模型和真实搜索 Provider 已配置。研究会按需要展示问题、文件计划和澄清；先回答阻塞问题，再等待继续。

在研究进度检查计划、搜索、证据整理、生成和失败事件。核对来源 Provider、链接和证据内容；`[MOCK SEARCH RESULT]` 或 `[MOCK]` 是测试材料，不是外部证据。联网研究常见基础交付文件包括 `README.md`、`RESEARCH.md` 和 `SOURCES.md`，其他文件由研究计划决定；需要执行方案时还可选择「生成方案」，先预览并确认文档清单。两条路径的文件数量规则各自独立。事实、模型建议和待确认假设应保持区分，引用编号本身不保证结论正确。

## 把研究文件交给工作区 Agent

### 选择技能并启动

1. 在「方案与文档」页签的「研究文档」检查并保存所需文件，点击「使用这些文档继续执行」。页面自动切到「执行工作区」，带入原目标，并从当前项目的技能列表中预选当前研究包已保存的文档。展开「项目技能文件」，核对文档及版本；你可以取消不相关文件，或选取本项目其他研究文档。点击交接不会自动创建执行任务。
2. 选择工作方式：「本地工作区」会交给配对的本机 Runner；「GitHub 仓库」会在服务器任务分支工作。两者不会互相导入文件。
3. 编辑已带入的「执行要求」，写清楚预期修改、不得修改的路径、需要生成的文件和验证目标。例如：

```text
根据选中的 PLAN.md 修复 src/calc.mjs 中的加法函数，新增 docs/REPORT.md 记录变更与验证。不要改 tests/、notes.md 或环境文件。先读取已有文件，再修改；验证失败时根据实际结果修复并重新检查。
```

4. 点击「开始执行」。服务端会固定所选技能的正文和版本。Agent 先读取工作区和每份所选技能，再开始文件修改。研究原文之后更新，不会改变已启动任务的技能快照。
5. 在对应任务卡查看进度、Agent 摘要、技能版本、语法检查和命令结果。本地测试命令仍须任务发起者在网页逐条批准，不能因点击交接而省略。每次文件修改都会使此前的验证结果失效，最终结果对应页面显示的快照版本。
6. 点击「查看文件与差异」，逐个检查实际变更。`completed` 不是人工验收、合并或推送的替代；本地模式不会创建 Git commit，GitHub 模式也不会自动合并或推送。

不选择任何 Markdown 也可以直接执行明确的工作区要求；但未选中的研究文件不会自动进入任务。若要先生成技能，可回到「方案与文档」使用任一路径保存文档，再显式交接并手动启动。

### 本地工作区：安装与配对 Runner

本地模式的文件读写发生在用户电脑上的 Runner 进程。Runner 随 ScenarioForge 源码提供，目前没有独立安装包或桌面目录选择器。每台运行 Runner 的电脑需要 Node.js 22.12 或更新版本、此版本 ScenarioForge 源码和 npm 依赖；要运行获批测试命令，还需要本机 Docker Desktop 及预先下载好的 `node:24-alpine` 镜像。

1. 在运行 ScenarioForge 源码的电脑上准备相同版本的仓库依赖：

```powershell
cd D:\path\to\ScenarioForge
npm ci
```

2. 浏览器打开项目中的「执行工作区」页签，选择「本地工作区」。展开「连接与运行设置」及其中的「连接新的本地目录」，填写便于识别的连接名并生成一次性配对码。
3. 在 Runner 所在电脑的 ScenarioForge 源码目录中运行网页显示的配对命令。将 URL、配对码和路径替换为当前页面给出的实际值：

```powershell
node --import tsx scripts/scenarioforge-local-runner.mjs pair --url https://your-scenarioforge.example --code ONE_TIME_CODE --directory "D:\my-project"
node --import tsx scripts/scenarioforge-local-runner.mjs run
```

4. 保持 Runner 终端运行。回到浏览器，等连接显示在线，选中连接和要使用的 Markdown 技能，再填写执行要求并启动任务。
   连接下方会显示 Runner 实际上报的目录，可展开或复制；任务卡记录本次启动时的目录。旧连接提示未上报时重启新版 Runner 即可，旧任务没有目录记录时会明确标为未知。
5. 若只做文件读写与静态语法检查，Runner 默认启动方式即可。若需要 Agent 请求并运行 Docker 命令，停止 Runner（`Ctrl+C`），然后以显式命令权限重新启动：

```powershell
node --import tsx scripts/scenarioforge-local-runner.mjs run --allow-commands
```

6. Runner 收到命令请求后，网页会显示完整 argv 和对应工作区版本。逐条检查后再决定批准或拒绝；拒绝或不可用的命令不能被 Agent 当成已运行。

本地开发可使用 `http://localhost:3000`。连接远程服务器必须使用本机信任证书的 HTTPS；Runner 不提供跳过 TLS 验证的开关，也不要求打开本机入站端口。配对码 10 分钟内一次性有效，Runner 凭证默认 30 天有效且可在网页撤销。凭证保存在 `%APPDATA%\ScenarioForge\runner.json`，不要分享或上传。默认 CLI 配置一次管理一个连接；重新配对前先停止旧 Runner。

### 本地目录读写和 Docker 命令的边界

- Agent 文件工具会直接写入你选定的本机目录。它不创建 Git 提交、不切换分支、不合并也不推送。开始前应确保有可恢复的备份或 Git 工作树。
- 当前只支持普通 UTF-8 文本，不支持二进制、符号链接/junction、`.git`、依赖/构建目录、私钥及非示例 `.env`。基线最多 300 个文件、每文件 40,000 字符、每次变更 20 个文件；一次命令快照最多 4 MiB。
- 需要真实命令时，命令必须在网页逐条批准，且只能交给本机 Docker 默认上下文。Docker 不可用、镜像缺失或快照超过限制时会报告未执行，不会回退到宿主机。应用不会自动下载镜像。
- 测试容器无网络、不挂载 `node_modules`，容器中对文件的写入会丢弃；要改项目文件必须由 Agent 文件工具提交变更。当前适合 Node 内置能力即可完成的测试，不适合依赖安装、联网、Python 环境或需要写入构建产物的验证。
- 容器有 CPU、内存、进程数、运行时间和输出上限。单条命令最长 60 秒，输出最多 64 KiB。每个 Agent 任务最多 24 个模型回合、10 分钟，最多三次启动/恢复；没有按金额设置的任务预算。
- Runner 启动提示已明确：获批命令由受限的无网络 Docker 容器运行，使用导出的临时快照，容器写入会丢弃。
- 文件命令、文件内容、必要的差异以及获批命令的 argv/输出会经过 ScenarioForge 服务端和模型供应商，因此本地模式不是完全离线执行，也不是操作系统级沙箱。服务器不复制整个本机目录。

### 审查、停止与恢复

执行任务卡展示「当前步骤」及具体操作时间线：等待模型、读取技能及版本、浏览和读取文件、保存新建/修改/删除、静态检查、等待审批、命令验证及差异审查。操作完成后显示实际耗时，可展开查看文件等细节。命令未批准或未执行会明确标识；不会把任务正在运行等同于测试已执行。旧任务只显示原先实际记录的事件，不补造详细操作。本地任务目录、差异和操作事件仅任务创建者可查看。

本地模式的文件变更直接落盘。任务结束后，网页展示的是任务保存的差异快照；Runner 离线时仍可查看，但你之后在本机继续修改不会自动更新这份历史快照。完成后请在本机用 Git 或其他方式检查、提交和推送。

停止会阻止后续操作，但已发送到本机的文件操作可能已经完成；多文件变更不是文件系统事务。遇到断线、超时或停止时，先检查本机当前文件，再决定是否从原任务恢复。恢复继续使用原始要求和冻结技能版本，不会自动采用新修改的 Markdown；要更换技能或目标，请新建任务。

### GitHub 仓库模式

1. 在项目「团队 Git 工作区」导入 GitHub 仓库。填写仓库 HTTPS 地址和可选分支，生成部署公钥，并由仓库管理员在该仓库 Settings → Deploy keys 中添加。只读操作可使用只读密钥；需要网页推送时开启写权限。
2. 导入完成后，在工作区 Agent 选择「GitHub 仓库」，确认目标项目仓库和技能，填写执行要求并启动。
3. Agent 的文件变更保存在服务器上的任务分支，审查前不会改共享 `main`。使用页面的文件和差异预览核对结果。
4. 审查通过后再到团队 Git 工作区选择任务分支并人工合并。推送 GitHub 另有明确确认步骤；任务完成不会自动合并或推送。

普通 GitHub 文件浏览、导入、分支和推送功能有各自的验收记录；新工作区 Agent 的 GitHub 完整执行、隔离验证、停止恢复和人工合并尚未做一次真实端到端联合验收。部署前请勿把这一模式当作已完成线上验证。

## RAG 与检索配置

RAG 是可选的研究证据检索功能，不是本地工作区 Agent 的运行前置条件。当前默认 `RAG_ENABLED=false`。不配置 Embedding 时，既有研究流程继续工作，但不会使用向量检索。

启用前需由平台维护者在服务端配置真实 Embedding Provider。聊天 API 可用不代表该服务支持 Embedding；Embedding 使用独立密钥，不会静默继承 `OPENAI_API_KEY`：

```env
RAG_ENABLED=true
EMBEDDING_PROVIDER=openai_compatible
EMBEDDING_BASE_URL=https://provider.example/v1
EMBEDDING_API_KEY=服务端专用的Embedding密钥
EMBEDDING_MODEL=服务商实际提供的Embedding模型名
```

变更前备份目标 MySQL，确认 `DATABASE_URL` 指向正确环境，再按部署流程生成 Prisma Client 和应用待执行迁移。先用独立测试库验证。历史资料需要回填时先运行 dry-run，再经确认使用 `npm run rag:backfill -- --apply`；完成配置并启动服务后，在研究包的「证据与检索」中重建索引。索引任务和回填可能调用 Embedding Provider 并产生费用。

`EMBEDDING_PROVIDER=mock` 只适用于测试，不代表语义检索有效。当前索引按研究包隔离，尚未合并同一团队项目内不同研究包；MySQL 向量使用应用内精确余弦扫描，尚无大规模性能基准。真实 Embedding 配置、真实资料检索质量与阈值仍待验收，详见 [RAG 说明](RAG.md)。

## 常见问题

### Runner 在页面显示离线

确认 Runner 终端仍运行、所选连接未被撤销、电脑能访问 ScenarioForge。使用远程服务器时确认地址为证书受信任的 HTTPS。配对码过期后回到页面重新生成，再执行新的 `pair` 命令；不要手动分享 `runner.json`。

### 配对后报地址或 TLS 错误

确认 `--url` 与浏览器打开的站点域名一致。远程服务器必须有本机信任的证书；不能用 IP 的 HTTP 页面冒充 HTTPS，也不要关闭证书校验。

### Agent 没有运行测试

查看审批卡和验证结果。如果 Runner 是用普通 `run` 启动，先停止并以 `run --allow-commands` 重启。确认 Docker Desktop 正在运行、Docker 默认上下文可访问，并且本地已存在 `node:24-alpine` 镜像。缺少环境时系统会标为未执行，不会自动下载镜像或切换为宿主机执行。

### 依赖型测试在 Docker 中失败

容器无网络且没有挂载 `node_modules`。安装依赖、构建产物写入、Python 测试或外部服务集成测试当前不属于这个沙箱的支持范围；查看错误后停止该命令请求，不要声称验证通过。

### 研究文件没有出现在技能列表

确认研究 Markdown 已经保存到当前项目的研究包，并刷新页面或切换到对应研究包。技能列表只包含当前项目用户有权限访问的文档，不会读取本机目录里任意的 `SKILL.md`。在工作区 Agent 中直接创建任务不会先生成研究文档。

### Agent 只聊天，右侧没有文档

检查「本次操作」是否为「生成方案」；「仅讨论」中的回复不会自动成为文件。已有对话可以点击右栏「根据当前需求规划文档」。预览只产生清单，需要在右栏点击「确认并生成 N 份文档」才会生成正文；清单出现非法名称、重名、手改目标或已过期提示时，先按提示处理。只有确认后才应出现 `documents_requested → documents_started`。此前修复过旧开发进程定时器仍使用旧 Worker 的问题：若确认后出现 `documents_requested → turn_started`，请让维护者检查调度版本；在确认无排队、运行任务后再重启服务，避免中断正在执行的工作。

### 方案生成报模型响应格式错误

这表示服务已返回内容，但其格式未通过解析或协议检查，不一定是密钥或网络问题。平台兼容完整 JSON 使用文本媒体类型返回，以及对象被额外 JSON 编码一次的情况；无效 JSON、错误协议或超限响应会明确停止，不自动重试。请先查看是否已有保存的文档；仍失败时让维护者检查服务端事件和响应格式，避免反复提交产生费用。2026-11-11 的一次原响应已恢复为 `PLAN.md` / `TASKS.md` v1，详细证据见[验收追记](PLAN_WORKFLOW_VALIDATION_20261111.md)。

### 页面显示 Mock 搜索结果

Mock 是测试 Provider。请让平台维护者在服务端配置可用的 `searxng`、`ddgs` 或 `tavily` Provider，并确认研究包没有把 Mock 证据当作真实来源。只有选择 Tavily 才需要 `TAVILY_API_KEY`。

### RAG 提示 Embedding 配置缺失或索引需重建

按上面的服务端配置补齐 Embedding 地址、专用密钥和模型名。Embedding 模型、端点、维度或分块配置变化后需要重建该研究包的索引。不要将聊天模型名称猜作 Embedding 模型，也不要在浏览器、Runner 命令或项目文件里放 Embedding 密钥。
