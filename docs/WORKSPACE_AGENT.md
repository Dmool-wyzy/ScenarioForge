# 研究技能与 Agent 工作区执行基线

**源码版本：2026-11-11，服务器部署待安排。** 当前包含可编辑清单、双页签、目录及详细进度。最新组合浏览器回归 42/42、另五项集成用例分次通过，方案离线回归 15/15；独立 MySQL、生产模式 Next.js、网页与 Runner 的联合验收通过，模型为本机 HTTP 夹具，独立 Node 测试 5/5。范围见[本版说明](RELEASE_NOTES_20261111.md)和[方案流程验收报告](PLAN_WORKFLOW_VALIDATION_20261111.md)。新入口的真实模型 + Docker 完整链路仍待授权验收；下文按日期保留旧阶段结果。

前端已增加「本地工作区」和「GitHub 仓库」两种方式。本地模式由本机 Runner 直接读写用户选择的目录，不要求 GitHub，连接步骤与当前边界见[本地 Runner 使用说明](LOCAL_RUNNER.md)。下文任务分支与容器验证流程描述的是服务器 GitHub 模式。

工作区执行链路支持输入目标 →「预览文档清单」→ 编辑并确认 1–20 份 Markdown → 生成正文并检查保存文件 →「使用这些文档继续执行」→ 确认要求和技能 → 手动「开始执行」→ 固定技能版本 → Agent 读取技能与工作区 → 在 GitHub 任务分支或用户本地目录修改文件 → 验证 → 审查差异 → 人工决定合并或提交。也可先聊天，或明确要求联网调研，再规划方案。交接只带入要求和所选已保存技能，清单本身不进入技能；交接不自动启动任务，也不跳过命令审批。没有改动现有模型、搜索、Embedding 或 RAG 配置。

## 使用方式

项目工作区分为「方案与文档」和「执行工作区」两个页签，顶部导航显示当前项目、工作方式与连接状态；本地方式显示目录与 Runner 在线状态，待审批命令有数量提示和直达入口。切换保留对话草稿、清单和文档编辑、执行要求、技能选择及任务差异状态，不自动提交任务。配对与命令运行说明收在执行页签的「连接与运行设置」中；当前任务展开，旧任务默认收在「历史任务」内。项目个人 Agent 收件箱默认收起，深链仍自动打开对应目标。

1. 准备执行目标：本地模式先配对 Runner 目录；GitHub 模式先在项目的「团队 Git 工作区」创建或导入仓库。Agent 操作的是选定目录或项目仓库，不是网站源码目录。
2. 在「研究与对话」首次输入或已有对话中选择「生成方案」，点击「预览文档清单」；右栏空态也可点击「根据当前需求规划文档」。默认推荐 `PLAN.md` 和 `TASKS.md`，按架构、接口设计、数据库、实验等明确关键词推荐更多模板，可修改名称、用途、要点，添加模板或自定义文件，最终保留 1–20 份。预览只用本地规则，不联网、不调用模型，也不是 AI 语义规划；点击「确认并生成 N 份文档」才用一次模型请求生成正文，无自动重试。也可选择「暂不生成」，或切换「仅讨论」再「发送」先聊天；普通聊天不强制研究。正文不表示已完成研究验证、项目修改或测试。
3. 在「方案与文档」页签的「研究文档」浏览、按需编辑并保存，下载单文件或 ZIP 是可选操作。点击「使用这些文档继续执行」，自动切到「执行工作区」，带入当前研究包的已保存技能和原目标。展开「项目技能文件」核对版本，可取消文件或选择同项目其他研究文档；执行要求仍可编辑。
4. 确认工作方式、目录或仓库和执行要求后，手动点击「开始执行」才会创建任务。交接不会自动执行；不选文档也能直接执行，未选择的文档不会自动进入本任务，本地命令仍须逐条审批。
5. 在执行页签的对应任务卡查看进度、执行摘要、技能版本、语法检查与命令结果；旧任务先展开「历史任务」。方案页签的研究进度不混入执行事件，每个任务只显示自身执行 ID 对应的日志。点击「查看文件与差异」审查实际文件。
6. 需要中断时点击「停止任务」，已保存的提交保留；「从原分支继续」使用原请求和技能快照，最多执行三次。若要使用更新后的技能或新要求，创建新任务。
7. 完成审查后，使用既有团队 Git 工作区选择任务分支并合并。任务完成不会自动合并或推送。

GitHub 任务可由项目成员查看，只有任务发起者或项目创建者能停止和恢复。本地任务目录、操作事件及差异只对发起者返回；项目创建者仍可按原权限停止任务，恢复本地任务仅限发起者。任务执行中仍持续检查发起者的项目权限。

任意所选目标文件已手动修改并保存后，生成器都不会覆盖；请移除该目标、换名或继续手动完善，未选的旧文件会保留。清单不允许重名、目录、非 `.md` 或系统保留文件名，文件名须以英文字母开头。生成前应保存或取消编辑并处理阻塞问题；预览后资料或文档变化会保留清单输入并禁止确认，须显式重新预览。生成期间资料、版本、编辑锁或租约变化时拒绝保存过期方案。研究文档与执行区分别在两个页签中展示，切换不会释放正在持有的文档编辑状态。

## Markdown 如何作为技能传入

前端选择的是文档 ID。服务端限定这些文档属于当前项目，并固定正文、来源研究、文件名、用途、版本和 SHA256。技能说明进入 Agent 初始上下文；正文由 `read_skill` 工具加载，所有已选技能读取完成前禁止修改文件。

GitHub 模式还把每份技能保存为 `.scenarioforge/skills/<快照标识>-<原文件名>.md`，可以通过任务分支审查；本地模式由 `read_skill` 读取服务端固定快照，不额外往所选目录写技能副本。原文后续编辑不会改变旧任务；恢复任务时也不重新读取最新原文。下载与否不影响这些步骤。

`PLAN.md`、`TASKS.md`、`TODO.md`、`CHECKLIST.md`、`*GUIDE.md`、`*WORKFLOW.md` 标为流程指导，其他 Markdown 标为研究参考。它们是 ScenarioForge 的任务技能文件，包含用途与来源信息；当前不自动转换为其他 Agent 客户端的标准 `SKILL.md` 包。研究参考仍需区分已知事实、模型建议和待确认假设。

## 实际执行与验证

新增执行 Agent 使用现有项目团队模型，工具包含列文件、读技能、读文件、提交变更、静态检查、隔离命令和差异审查。GitHub 文件修改使用 Git 对象和临时索引形成原子提交，任务分支为 `work/<成员ID>/agent-<任务ID>`。共享 `main` 与其他任务分支不被执行工具修改。本地模式直接写入选定目录，不创建提交。

- 已有文件必须先读取；提交校验当前 head，防止覆盖其他操作。每次提交至多修改 20 个文件。
- 语法检查仅解析 JS、TS 和 JSON，**不检查类型、不运行程序，也不代表测试通过**。没有适用文件时显示未完成验证。
- 实际测试命令通过 Docker 运行。需要服务器已有可用 Docker 及本地 `node:24-alpine` 镜像；程序不自动下载镜像或安装依赖。不可用时明确记录「命令未执行」。
- 本地模式中，Agent 请求执行命令后须由任务创建者在网页逐条批准原始 argv 和对应文件版本；Runner 也必须用 `run --allow-commands` 显式启动。命令只交给本机 Docker 默认上下文运行，并拒绝远程 Docker 端点；缺少 Docker 或镜像时明确记录「命令未执行」，不会退回宿主机执行。
- 本机容器无网络、无应用密钥、以非 root 用户运行；镜像根目录只读，安全文件快照只读挂载到 `/input`，容器将其复制到限额的临时可写目录 `/workspace`。容器和临时快照退出后会清理；工作区副本中的命令写入会丢弃。生成或修改项目文件必须使用文件变更工具。
- 每条命令最多 60 秒、stdout/stderr 合计最多 64 KiB；容器限制 CPU、内存、进程数。快照最多 300 个 UTF-8 文件、4 MiB，过滤 Git 元数据、依赖、构建目录、环境文件、凭据和符号链接。不自动联网或安装依赖，因此当前适合 Node 内置能力可完成的测试。
- 当前容器适合 `node --test tests/example.test.mjs` 等不需安装依赖、只读源码的验证。需要依赖安装、构建产物写入、Python 或其他语言环境的工程还需后续扩展。
- 每次文件变更使旧验证失效；最终检查由服务端主动执行。前端分别展示语法检查和命令结果，不采信模型自述的「测试通过」。

`completed` 只表示本轮有文件变更、最终语法检查通过，且已尝试的命令没有失败或缺失；仍需要人工审查。只有语法通过时，页面会仅显示语法通过。验证不适用、命令不可用或没有实际产物的任务进入 `review`。

## 初始化与配置

新增 `WorkspaceExecution` 表保存任务、版本快照、分支、租约和检查记录。迁移文件为 `prisma/migrations/20261110090000_workspace_execution/migration.sql`。迁移已在用户同意的本机临时 MySQL 8.0.45 实例和服务器独立 MySQL 8.4.13 测试库验证，生产库尚未应用。

在准备好的项目专用 MySQL 环境中，沿用现有流程生成客户端并应用迁移，再启动应用：

```powershell
npm run db:generate
npm run db:deploy
npm run dev
```

`db:deploy` 会应用目标数据库全部待执行迁移，请使用为当前环境准备的数据库。迁移未应用时，前端显示功能尚未启用，原有研究流程可继续使用。执行依赖已有任务调度器，`SCENARIOFORGE_TASK_SCHEDULER=off` 时不会消费队列。

执行端必须能读取项目仓库目录 `SCENARIOFORGE_GIT_ROOT`。本功能不通过旧的本地开发仓库转发接口执行远端任务；如果本地网页只连接服务器数据库而仓库仍在服务器，应在持有仓库的服务器运行执行端。RAG 不属于执行链路的必需条件，配置可以后续补齐。

`SCENARIOFORGE_EXECUTION_EXPORT_ROOT` 指定容器验证快照的专用父目录。未设置时使用操作系统临时目录；使用 `PrivateTmp=yes` 的 systemd 服务应配置位于私有 `/tmp` 之外、服务进程与本机 Docker daemon 都可访问的宿主绝对路径。路径各级不能是符号链接；专用父目录须属于服务用户，在 Linux 上使用 `0700` 权限，不能使用文件系统根目录或包含 `..`、逗号、换行等无效路径。程序在其中创建每次验证的私有快照，仅将只读工作区子目录挂入容器。

本次服务器验收使用 `/home/ubuntu/scenarioforge-acceptance/private/exports`，属主为 `ubuntu`、权限为 `0700`。Docker daemon 访问权限与导出目录配置是两个独立条件：验收只给临时容器测试单元增加了 `SupplementaryGroups=docker`，没有调整线上 Web 服务的权限或配置。

## 当前限额与边界

- 单个工作区基线最多操作 300 个可访问文件，单次文件读取至多 40,000 字符。
- 每任务最多 20 份技能、正文共 60,000 字符；执行要求最多 5,000 字符。
- 每次执行最多 24 个模型回合、每回合最多 8,192 输出 token、总时限 10 分钟，最多三次启动/恢复。没有按金额设置项目预算。
- 验证容器导出内容最多 4 MiB；二进制、符号链接和子模块不参与执行，敏感路径和技能快照不可由 Agent 改写。
- 任务和租约持久化，进程重启后可接管过期任务。沿用当前单 Web 进程的仓库操作锁，扩为多进程前需增加共享仓库锁和严格的全局并发协调。
- 本地命令最长运行 60 秒，stdout/stderr 合计不超过 64 KiB；停止、断线、撤销或授权失效会终止进程树。命令修改可访问文件时自动标为失败并保存差异，须重新验证。
- 此版本没有新增外部 Agent/MCP 接入、自动拉取环境、自动合并、自动发布、桌面目录选择或独立安装包。

## 独立环境验收与后续范围

三种验收各自检查不同内容：MySQL 测试库检查真实任务保存、排队、停止恢复和权限；真实模型检查实际服务能否读技能、操作文件并完成要求；Docker 检查生成代码的真实测试与运行隔离。数据库验收可以使用确定性测试模型，不消耗模型 API 额度；这不代表真实模型已经验收。

已准备下列入口，均不自动加载 `.env.local`，也不自动安装环境或迁移数据库：

| 入口 | 启动条件 | 检查范围 |
| --- | --- | --- |
| `npm run check:workspace-agent-db` | 显式提供相同的 `SCENARIOFORGE_TEST_DATABASE_URL` 和 `DATABASE_URL`，库名以 `scenarioforge_test_` 开头 | 真实 MySQL、临时 Git 仓库、确定性模型；权限、并发互斥、停止恢复、租约接管和验证记录 |
| `npm run check:workspace-agent-container` | 显式设置 `SCENARIOFORGE_TEST_DOCKER=1`，本地 Docker 和已有 `node:24-alpine` | 实际 `node --test` 失败与修复后通过，以及容器用户、源码只读、凭据与敏感文件隔离 |

MySQL 脚本只清理自己创建的测试记录，不清空数据库。Docker 脚本拒绝远程 Docker context，运行环境缺失时明确失败，不能把“没有运行”算作通过。Windows 本地文件测试只验证内容与路径；Linux 权限和实际容器行为已在下述服务器隔离环境验证。
